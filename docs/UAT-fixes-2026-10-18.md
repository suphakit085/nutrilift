# ผลแก้ปัญหาจาก UAT — 18 ตุลาคม 2569

## สิ่งที่แก้แล้ว

ดำเนินการตามลำดับจากแผน remediation: สถานะเครื่องมือและข้อความผิดพลาด → ชื่ออาหารและที่มา → เตรียมรุ่นเมนู → ตรวจความพร้อม auth แยกต่างหาก

| ปัญหา | พฤติกรรมหลังแก้ |
|---|---|
| แสดง ✓ แม้จัดเมนูไม่ได้ | Backend กำหนด `status` จากผลเครื่องมือจริง ส่งใน SSE และเก็บใน `tool_calls`; หน้าเว็บและประวัติแยกสำเร็จ/บางส่วน/ผิดพลาด/รอยืนยัน/ไม่พบข้อมูล |
| จัดตารางได้แต่สารอาหารยังขาด กลับดูเหมือนสำเร็จครบ | แสดง “จัดตัวอย่างเมนูแล้ว ยังเข้าเป้าไม่ครบ” พร้อมส่วนต่างเดิม; ✓ ใช้เฉพาะผลสำเร็จที่ระบุชัด |
| ประวัติเดิมไม่มีสถานะ | แสดง “ประมวลผลคำขอแล้ว” เป็นกลาง ไม่เดาผลสำเร็จจากข้อความ |
| ข้อความ error หลุด “ให้บอกผู้ใช้…” | เปลี่ยนข้อความไม่มีแหล่งโปรตีน/ไม่มีโปรไฟล์/ข้อจำกัดสุขภาพให้เป็นคำอธิบายถึงผู้ใช้โดยตรง; ไม่ผ่อนการกรองอาหารแพ้ |
| ผู้ใช้พิมพ์ชื่อเต็ม แต่โมเดลลบ comma แล้วต้องยืนยันซ้ำ | ถ้า partial มีชื่อ canonical ที่ผู้ใช้ระบุชัดเพียงรายการเดียว จะค้นชื่อจริงซ้ำ; ชื่อกำกวม หลายอาหาร ชื่อที่ถูกปฏิเสธ และชื่อสั้นซ้อนชื่อยาวไม่ถูกอนุมัติโดยเดา |
| ขอที่มาแล้วไม่มี | คำตอบคำนวณตามน้ำหนักแสดงชื่อฐานและรหัส source เดิม; ถ้าไม่มี source แจ้งตรง ๆ; คงคำเตือนค่าประมาณและสถานะรอผู้ตรวจทาน |

ไม่ได้เปลี่ยนค่าคุณค่าทางอาหาร เพิ่มสูตรอาหาร หรือเพิ่ม migration/dependency ในแพตช์นี้ ลิงก์รายการจากเว็บต้นทางยังตรวจยืนยันไม่ได้ จึงแสดงรหัสแหล่งข้อมูลจริงโดยไม่สร้าง URL ขึ้นเอง

พบและแก้เพิ่มระหว่างทดสอบ:

- “ขอ 7 มื้อ ไม่เพิ่มมื้อเสริม” เคยถูกเปลี่ยนเป็น 3 มื้อ: คงจำนวนที่ระบุและปฏิเสธ 7 มื้อซึ่งยังไม่รองรับ; คำขอปฏิเสธมื้อเสริมในรอบถัดไปยังกลับเป็น 3 มื้อได้ตามเดิม
- “แพ้นมวัวและแพ้ถั่ว” เคยรวมคำว่าแพ้ซ้ำเป็นข้อจำกัดที่ไม่รู้จัก: แยกทั้งสองการแพ้อย่างถูกต้อง ไม่สร้างเมนูเมื่อไม่มีอาหารผ่านข้อจำกัด

ทั้ง 6 สถานการณ์ทดสอบผ่านการพิมพ์ใน UI จริง ตรวจคำตอบที่บันทึกในฐาน เปิดประวัติใหม่ และตรวจหน้าจอ 390px:

1. ขอ 7 มื้อ → ปฏิเสธและ badge ผิดพลาด ไม่มี ✓
2. `อกไก่ไม่มีหนัง, ต้ม 100 กรัม` พร้อมขอที่มา → ตอบรอบแรก 151 kcal, โปรตีน 29 กรัม, `USDA-FDC-SR:171478`, แสดงว่ารอผู้ตรวจทาน
3. ชื่ออกไก่เรียงใหม่ไม่ตรงชื่อจริง → รอยืนยัน ไม่มีตัวเลขยืมจากอาหารใกล้เคียง
4. ผู้ใช้พลังงานสูง ขอ 3 มื้อและไม่รับมื้อเสริม → แจ้งยังเข้าเป้าไม่ครบ พร้อมส่วนต่าง
5. ผู้ใช้เดิมยอมรับจัดตามความเหมาะสม → 3 มื้อหลัก + 3 มื้อเสริม พร้อมสถานะสำเร็จ
6. วีแกน แพ้นมวัวและถั่ว → แจ้งไม่มีแหล่งโปรตีนที่ผ่านข้อจำกัด ไม่มีตารางอาหารหรือคำสั่งภายในหลุด

มีการแก้ตัวทดสอบไดอารี่ให้ชี้ API origin ตรงกับ frontend build ที่ใช้ทดสอบ และทดสอบข้อความแพ้อาหารซ้ำหลังแก้ parser; ตัวเลขข้างต้นเป็นผลรอบสุดท้าย ไม่รวมรอบตั้งค่าผิดหรือรอบที่ยังพบปัญหา

## Workspace หลักและ auth

ย้ายเฉพาะแพตช์กลับ workspace หลักแล้ว โดย merge ส่วนที่ทับกับ auth/retrieval แยก ไม่คัดลอกทับทั้งไฟล์ `api.ts` หรือหน้าแชต ตรวจ hash ของงานค้างอื่น **1,051 ไฟล์ตรงกันก่อนและหลัง**

- Compatibility กับ workspace ที่มี auth ใหม่: backend **93 ผ่าน, 13 deselected**; frontend **83 ผ่าน** และ `tsc --noEmit` ผ่าน
- Auth PostgreSQL จริงบนฐานทดสอบชั่วคราว: **27 ผ่าน, 13 deselected**; ครอบคลุม Alembic ถึง head `f16c6106a001`, schema ตรง ORM, upgrade บัญชีเดิม, single-use link และ concurrent session/password operations
- การทดสอบ auth นี้ใช้การดักอีเมลในชุดทดสอบ **ยังไม่ได้ส่งอีเมลผ่าน Resend เข้ากล่องจริง**
- ตรวจ Google DNS รอบนี้ยังได้ NXDOMAIN สำหรับ `nutrilift.xyz` และ record ของ Resend ที่ตรวจ; local configuration ที่เข้าถึงยังไม่มี `RESEND_API_KEY` และผู้ส่ง ไม่ใช่การอ่าน Variables ใน Railway และไม่ใช่หลักฐานว่า Railway ตั้งค่าเหมือน local

## สถานะ release และงานที่ยังเหลือ

**แก้โค้ดและตรวจ candidate แล้ว ยังไม่ได้ push/deploy Production** ผลทั้งหมดในรายงานนี้ไม่ใช่การรับรองรุ่นออนไลน์ GitHub `main` ที่ตรวจล่าสุดยังเป็น `798b7f5`

รุ่นเมนูเตรียมไว้ใน branch แยกข้างต้น พร้อม regression tests; ไม่มี migration ใหม่ ใช้ release chain เมนูเดิมบวกแพตช์ UAT นี้ หลังปล่อยต้องตรวจ frontend/backend ใช้ commit ที่เข้าคู่กัน และทำ smoke test เมนู/ประวัติ/ไดอารี่บนระบบจริงก่อนปิดช่องว่าง deployment

Auth ต้องเป็น release แยก: รอ DNS/Resend verified, ตั้งค่า sender/key ใน staging อย่างปลอดภัย, ส่ง verification/reset เข้ากล่องอีเมลทดสอบที่ควบคุมได้จริง, ตรวจลิงก์ใช้ซ้ำ/หมดอายุและการยกเลิก session แล้วจึง rollout migration กับ frontend/backend ที่เข้าคู่กัน บัญชีเดิมไม่ถูกทำเครื่องหมาย verified โดยไม่มีหลักฐานเจ้าของอีเมล

ขอบเขตปริมาณอาหารยังเป็นนโยบายเริ่มต้นของระบบที่รอนักกำหนดอาหารทบทวน ไม่รับรองว่าเมนูเหมาะสมทางคลินิกทุกบุคคล
