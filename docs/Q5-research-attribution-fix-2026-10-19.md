# Q5: แก้การระบุผู้แต่งของข้อสรุปเรื่องไขมัน

## ปัญหาและต้นเหตุ

UAT เว็บจริงพบคำตอบที่ระบุ Helms (2014) กับ Aragon (2017) ร่วมกันก่อนอธิบายช่วงไขมัน 15–20% ในบางกรณีเตรียมแข่งขันเพาะกาย ตรวจ [Helms 2014 ส่วน Fat](https://link.springer.com/article/10.1186/1550-2783-11-20) พบข้อความเงื่อนไขนี้โดยตรง ส่วน [Aragon 2017](https://link.springer.com/article/10.1186/s12970-017-0174-y) ใช้รองรับเรื่องรูปแบบอาหารและองค์ประกอบร่างกายคนละประเด็น

ต้นทาง `energy-balance-cut-bulk.md` เคยใส่ชื่อทั้งสองงานรวมท้ายย่อหน้าของข้อสรุปเรื่องไขมัน จึงทำให้ AI เชื่อมข้อสรุปกับผู้แต่งกว้างเกินหลักฐาน ข้อมูล RAG ที่ production ใช้ตรงกับข้อความต้นทางเก่าจริง ไม่ใช่เพียงข้อผิดพลาดบนหน้าจอ

## การแก้

- แยกข้อความโปรตีน/การรักษามวลไร้ไขมันออกจากข้อความช่วงไขมัน และผูกแต่ละย่อหน้ากับส่วนที่เกี่ยวข้องใน Helms 2014
- ช่วงไขมัน 15–20% ระบุเฉพาะ Helms และคงเงื่อนไขเรื่องบริบทเตรียมแข่งขัน โปรตีน/คาร์โบไฮเดรต และไม่ใช่ขั้นต่ำสำหรับทุกคน
- เก็บ Aragon ไว้กับย่อหน้ารูปแบบอาหารที่งานนั้นรองรับ ไม่ลบงานออกจากบรรณานุกรมของทั้งการ์ด
- เพิ่มกติกาทั่วไปใน prompt v1.19.0: ผู้แต่ง/ปีต้องตรงกับข้อสรุปนั้น รายชื่อหลายงานไม่แปลว่ารองรับทุกประโยค ถ้าระบุไม่ได้ให้บอกข้อจำกัด ไม่เดา ไม่แทนชื่อผู้แต่งในคำตอบด้วย regex
- เก็บ hash ก่อน/หลังใน `knowledge/releases/q5-attribution-v1.json` โดยไม่แก้ manifest หลักฐานเก่า ใช้การตรวจ hash เดิมร่วมกับ correction ใหม่ตรวจอาหารความรู้อีก 25 การ์ดด้วย

ไม่ได้เปลี่ยนสูตรคำนวณ ข้อมูลอาหาร ปริมาณอาหาร UI หรือระบบ auth ไม่ต้องเพิ่ม Variables หรือ migration

## การตรวจ

- Backend regression: **1594 ผ่าน**, 76 deselected ตามขอบเขตเดียวกับ CI; Ruff ผ่าน
- Tests ใหม่ตรวจย่อหน้าที่ผูกข้อสรุปกับ Helms, การเก็บ Aragon ในหัวข้อที่ถูกต้อง, hash chain และกติกาผู้แต่งที่ใช้กับหลาย S label
- Gemini จริงกับ retrieved passages จริงที่แทนเฉพาะ chunk จากการ์ดฉบับแก้ในหน่วยความจำ: Q5 **4 รูปคำถาม × 2 รอบ = 8 คำตอบ** และคำถามควบคุมโปรตีน/ครีเอทีนอีก 2 คำตอบ เก็บคำตอบทุกฉบับ ไม่ใช้ keyword ผ่านเพียงอย่างเดียวแทนการอ่าน
- Q5 ที่ทดสอบครอบคลุมคำถามต้นเหตุ, ถามผู้เสนอช่วงไขมัน, ตั้งสมมติฐานผิดว่า Aragon เสนอช่วงนี้ และขอเปรียบเทียบ Aragon/Helms คำตอบระบุ Helms สำหรับข้อสรุปนั้นหรือบอกว่าข้อมูลที่ดึงไม่พอเปรียบเทียบ ไม่รวมผู้แต่งเป็นข้อสรุปเดียวกัน

การทดลองชุด candidate เป็นการอ่านฐานข้อมูลแบบ read-only จึงยังไม่ถือว่าฐานความรู้ production เปลี่ยนแล้ว กระบวนการ release ต้อง sync ข้อมูลด้านล่างและตรวจซ้ำก่อนสรุปผล

## การเผยแพร่ข้อมูล RAG

การ deploy backend เพียงอย่างเดียวไม่ re-ingest การ์ด จึงต้องอัปเดตทั้งต้นทางใน Git และข้อมูล RAG ที่เว็บใช้ กระบวนการที่เตรียมไว้ใน `output/q5-attribution-20261019/` ตรวจว่า document และ chunks ตรงกับฐานก่อนแก้, สร้าง embedding ใหม่ให้ **1 chunk จากทั้งหมด 6 chunks** ของการ์ดนี้ แล้วอัปเดต chunk เดิมกับ document content hash ใน transaction เดียว ไม่มีการลบ/rebuild ทั้งคลัง

ใช้ frozen plan และข้อมูลเดิมสำหรับ rollback ตรวจ fingerprint ของเอกสาร/chunks อื่น อาหาร และข้อมูลผู้ใช้ก่อน/หลัง ต้องตรงกันทั้งหมด จากนั้นทดสอบ retrieval และ Gemini กับข้อมูลหลัง sync โดยไม่แทน passage ในหน่วยความจำ หลักฐานจะถูกเก็บแยกจากชุด candidate ไม่ใช้ผลก่อน sync อ้างว่าขึ้น production แล้ว

ผล CI, commit รวม, ผล sync และผลตรวจหลัง sync อยู่ใน `output/q5-attribution-20261019/` ส่วนการตรวจเบราว์เซอร์ผ่าน API ที่ deploy แล้วต้องรายงานแยกหากยังไม่ได้ทำ ไม่ใช้ผลเรียก engine โดยตรงอ้างว่าเป็น end-to-end ผ่าน Railway

## ขอบเขตผล

แก้ต้นเหตุและตรวจคำถามต้นเหตุซ้ำ ไม่รับประกันว่าคำตอบ AI ทุกคำถามจะไม่มีการระบุผู้แต่งคลาดเคลื่อน งานนี้ไม่ได้ตรวจทานบรรณานุกรมหรือข้อสรุปทั้งหมดในฐานความรู้ใหม่ และไม่ใช่การอนุมัติทางคลินิก
