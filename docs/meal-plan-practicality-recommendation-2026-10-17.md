# ข้อเสนอปรับความเหมาะสมของแผนอาหาร NutriLift

วันที่ตรวจ: 17 ตุลาคม 2026 — สถานะขณะจัดทำข้อเสนอ: วิเคราะห์โค้ด ทดลอง baseline และเสนอแบบ ก่อนปรับตัวจัดเมนูรุ่นใหม่

ภายหลังนำข้อเสนอช่วงแรกไปพัฒนาและทดสอบแล้ว ดู [บันทึกการเปลี่ยนแปลงและผลทดสอบ](meal-plan-practicality-change-2026-10-17.md) ข้อเสนอและ baseline ด้านล่างเก็บไว้ตามช่วงเวลาก่อนพัฒนา

## ข้อเสนอหลัก

คงการคำนวณสารอาหารด้วย Python จากฐานข้อมูลเดิม เพิ่มขอบเขตปริมาณอาหารที่มีที่มา และเป้าหมายรายมื้อเข้าไปในตัวจัดเมนู เลือกโครงสร้าง 3 หรือ 4 มื้อตั้งแต่ก่อนคำนวณ แล้วเปรียบเทียบผลก่อน/หลังอย่างแยกเกณฑ์ ต่อเมื่อพบว่าวิธีเดิมแก้ข้อจำกัดเหล่านี้ได้ไม่ดี จึงพิจารณาเปลี่ยน optimizer เป็น mixed-integer linear programming (MILP)

นี่เป็นข้อเสนอทางวิศวกรรมที่อิงสภาพโปรเจกต์และงานวิจัยด้านล่าง ไม่ใช่ผลทดลองที่พิสูจน์แล้วว่าวิธีใหม่เหนือกว่า หรือการรับรองทางคลินิก

## สิ่งที่ตรวจพบในโปรเจกต์

อ้างอิง `backend/app/services/meal_plan.py`:

| จุด | พฤติกรรมปัจจุบัน | ผลต่อปัญหา |
| --- | --- | --- |
| `PORTION_STEP`, `Slot`, `MEAL_TEMPLATE` | ปรับปริมาณเป็นช่วง 0.25 เท่าของหน่วยอ้างอิง พร้อมขอบเขตตามบทบาทอาหาร | หากข้อมูลอ้างอิง 100 กรัม ขั้นหนึ่งคือ 25 กรัม ซึ่งไม่ใช่ขนาดรับประทานที่เหมาะกับอาหารทุกชนิด |
| `_Item.__post_init__` | มีข้อจำกัดกรัมและกฎเฉพาะ เช่น น้ำมัน/ผงอาหารเสริม รวมถึงอาหารนับหน่วย | มีการควบคุมปริมาณอยู่แล้ว แต่ยังไม่ใช่นโยบายรายอาหารที่ผ่านการทบทวนครบถ้วน |
| `_error` | ให้คะแนนความคลาดเคลื่อนของพลังงาน โปรตีน คาร์โบไฮเดรต และไขมันรวมทั้งวัน | ยังไม่มีคะแนนการกระจายพลังงาน/โปรตีนระหว่างมื้อ หรือความเหมาะสมของปริมาณ |
| `_optimize` | coordinate descent ปรับปริมาณอาหารที่เลือกแล้ว | ไม่มีการสลับชนิดอาหารระหว่างการ optimize และไม่รับประกันคำตอบดีที่สุดทั้งหมด |
| `build_day_plan`, สาขา `meal_count == 3` | คำนวณแผน 4 มื้อก่อน แล้วค่อยย้ายของว่างเข้า 3 มื้อหลัก | ยอดรวมทั้งวันยังเท่าเดิม แต่บางมื้ออาจมีอาหารและโปรตีนกระจุกตัว |

คำว่า `serving_g` ในฐานข้อมูลต้องตีความตามแหล่งข้อมูล: หน่วยอ้างอิงคุณค่าทางโภชนาการ เช่น 100 กรัม ไม่เท่ากับขนาดหนึ่งมื้อที่ควรแนะนำเสมอไป การแก้ควรแยกข้อมูลสองประเภทนี้ ไม่แก้ตัวเลขสารอาหารต้นฉบับเพื่อให้ปริมาณดูดี

## ผล baseline ที่รันครั้งนี้

- ชุดนี้ประกอบด้วย 2 เพศ × 3 เป้าหมาย × 9 ชุดข้อจำกัดอาหาร × 3 variants ใช้จำนวนมื้อเริ่มต้น 4 มื้อ

- เป็นผลจากโค้ดและข้อมูลใน workspace ขณะตรวจ ไม่ใช่การทดสอบ HTTP ของ deployment จริง

## งานวิจัยและเครื่องมือที่ใช้ประกอบ

1. **Benvenuti & De Santis (2020)**, *Making a Sustainable Diet Acceptable: An Emerging Programming Model With Applications to Schools and Nursing Homes Menus*. ใช้สูตรอาหารที่มีขนาดส่วนกำหนดไว้ จัดลงช่องมื้อ และพิจารณาความหลากหลาย/การยอมรับควบคู่คุณค่าอาหาร หลักการนี้เหมาะกับการเพิ่มโครงสร้างมื้อและ portion policy แต่บริบทโรงเรียน/สถานดูแลผู้สูงอายุไม่ใช่หลักฐานยืนยันผลกับผู้ใช้ NutriLift โดยตรง [บทความต้นฉบับ](https://www.frontiersin.org/journals/nutrition/articles/10.3389/fnut.2020.562833/full)
2. **Sklan & Dariel (1993)**, *Diet planning for humans using mixed-integer linear programming*, British Journal of Nutrition 70(1):27–35. แบบจำลองรวมข้อกำหนดสารอาหาร ความถี่อาหาร พลังงานแต่ละมื้อ และอาหารที่ต้องเป็นจำนวนเต็ม สนับสนุนแนวทางใช้ MILP เป็นตัวเปรียบเทียบ การตั้งข้อจำกัดยังต้องอาศัยข้อมูลที่เหมาะกับโครงการนี้ ปี 2007 ที่หน้าเว็บคือวันเผยแพร่ออนไลน์ ไม่ใช่ปีวารสาร [บทคัดย่อต้นฉบับและข้อมูลวารสาร](https://www.cambridge.org/core/journals/british-journal-of-nutrition/article/diet-planning-for-humans-using-mixedinteger-linear-programming/E84EB86429B293CF732EE63DB7D2CBCD)
3. **Jäger et al. (2017)**, *International Society of Sports Nutrition Position Stand: protein and exercise*. กล่าวถึงการกระจายโปรตีนระหว่างวันและปริมาณต่อครั้งที่ขึ้นกับบริบท ใช้เป็นเหตุผลให้ประเมินการกระจายรายมื้อ ไม่ใช้ช่วง 20–40 กรัมเป็นเพดานบังคับสำหรับทุกคน และต้องแยกกรัมโปรตีนออกจากกรัมน้ำหนักอาหาร [บทความต้นฉบับ](https://link.springer.com/article/10.1186/s12970-017-0177-8)
4. **SciPy `optimize.milp`** เป็นเครื่องมือที่ทดลองแบบจำลองจำนวนเต็มได้ ใช้ HiGHS และมีสถานะ optimal/infeasible/time limit ให้ตรวจ ต้องตรวจผลและ constraint ซ้ำก่อนแสดงแก่ผู้ใช้ ตัว solver ไม่รับรองความเหมาะสมของนโยบายอาหารที่ป้อนเข้าไป [เอกสารทางการ](https://docs.scipy.org/doc/scipy/reference/generated/scipy.optimize.milp.html)

## รูปแบบที่แนะนำสำหรับรุ่นถัดไป

1. **แยก planning portion ออกจาก nutrient reference**: metadata ตาม food ID ระบุน้ำหนักสุก/ดิบ หน่วยนับ ช่วงปริมาณที่อนุญาต ช่วงปริมาณที่ต้องการ แหล่งอ้างอิง และสถานะผู้ทบทวน ใช้แหล่งเดียวกันในการแสดงผลและคำนวณ ไม่อนุมานจากชื่ออาหารอย่างเดียว อาหารที่ยังไม่มี policy ให้ใช้เฉพาะเมื่อมี fallback ที่ระบุสถานะชัดเจน หรือคัดออกจากชุดแนะนำที่ต้องผ่านเกณฑ์นี้
2. **สร้าง template ตามจำนวนมื้อก่อน solve**: โหมด 3 มื้อคำนวณ 3 มื้อโดยตรง โหมด 4 มื้อมีของว่างตามสัดส่วนที่กำหนด ไม่ย้ายอาหารหลัง optimize แล้วถือว่าสมดุลเดิม
3. **แยกข้อห้ามจากความชอบ**: ตัวกรองการแพ้/ข้อจำกัดอาหาร คุณภาพข้อมูล หน่วยนับ และขอบเขตปริมาณที่รับรองเป็นข้อบังคับ ส่วนการกระจายพลังงาน/โปรตีน ปริมาณที่คุ้นเคย และความซ้ำเป็นคะแนนความเหมาะสมที่ปรับได้ ไม่บังคับทุกมื้อเท่ากัน
4. **จัดอันดับคำตอบเป็นลำดับ**: ผ่านข้อบังคับก่อน จากนั้นให้ความสำคัญกับการผ่านช่วงสารอาหารรายวัน แล้วเลือกคำตอบที่ได้คะแนนความเหมาะสมรายมื้อดีกว่า การให้น้ำหนักแบบรวมอย่างเดียวอาจยอมเสียเป้าสารอาหารเพื่อคะแนนอื่น จึงต้องมีเกณฑ์ผ่านแยกต่างหาก
5. **เปิดทางสลับอาหาร**: ทดลองชุดอาหารทดแทนแบบจำกัดจำนวนและทำซ้ำได้ เมื่อชุดแรกไม่สามารถทำตามเกณฑ์ ไม่ขยายขนาดอาหารจนหลุด policy เพื่อให้ยอดรวมดูผ่าน
6. **ตรวจคำตอบหลังปัดหน่วยและจัดมื้อสุดท้าย**: คำนวณจากอาหาร/กรัมจริงซ้ำ ตรวจ bounds จำนวนเต็ม ข้อจำกัดอาหาร โครงสร้างมื้อ และสถานะข้อมูล หากยังทำแผนตามเกณฑ์ไม่ได้ให้บอกข้อจำกัดตรงไปตรงมา ห้ามผ่อนข้อห้ามการแพ้เพื่อให้ได้สารอาหารครบ

ในระยะแรกยังใช้ coordinate descent ได้ แต่ต้องเปลี่ยน objective/การจัดมื้อและเพิ่ม validator ตามข้างต้น หากทดลอง MILP ต้องใช้ชุดอาหารและข้อจำกัดเดียวกันเพื่อเปรียบเทียบอย่างยุติธรรม Objective แบบ squared error เดิมไม่ใช่ linear objective โดยตรง; จะใช้ MILP ต้องนิยาม absolute deviation ด้วย auxiliary variables หรือประกาศวิธีแปลง objective ให้ชัด ไม่อ้างว่าเทียบ objective เดิมได้เหมือนกันโดยอัตโนมัติ

ระยะยาวเพิ่มเมนูอาหารไทยจากสูตรและส่วนผสมที่ตรวจสอบได้ จะช่วยเรื่องความเข้ากันของอาหารมากกว่าการจับคู่สารอาหารอย่างเดียว แต่ต้องทำข้อมูลสูตร ปริมาณหลังปรุง และทดสอบเพิ่มเติม จึงควรเป็นงานต่อจากการแก้ครั้งแรก

## การทดสอบก่อนเลือกวิธีและเผยแพร่

- เก็บ baseline แบบระบุเวอร์ชันโค้ด ข้อมูลอาหาร portion policy โปรไฟล์ variants และ outputs ให้ทำซ้ำได้
- รัน 162 กรณีเดิม พร้อมขยายให้ครอบคลุมทั้ง 3/4 มื้อ พลังงานต่ำ/สูง วีแกน การแพ้ร่วม อาหารนับหน่วย น้ำหนักสุก/ดิบ และกรณีที่ข้อจำกัดไม่มีคำตอบ
- แยกผล: ความถูกต้องของการคำนวณและหน่วย / การละเมิดข้อบังคับ / อัตราผ่านสารอาหารรายวัน / การกระจายรายมื้อ / ปริมาณตาม policy / เวลาคำนวณ / การยอมรับของผู้ใช้
- ตั้งเกณฑ์ว่าแผนที่แสดงเป็นคำแนะนำผ่านข้อบังคับทุกข้อ และไม่แสดงสถานะผ่านรายวันหากสารอาหารไม่ผ่านจริง เป้าหมายเวลาและคะแนนความเหมาะสมต้องกำหนดก่อนดูผลทดสอบชุดสุดท้าย
- แยกชุดใช้ปรับกฎออกจากชุดประเมินจริง และให้ผู้เชี่ยวชาญโภชนาการกับผู้ใช้เป้าหมายเปรียบเทียบแผนเก่า/ใหม่แบบไม่ระบุชื่อวิธี
- หากผลของวิธีเดิมที่ปรับแล้วไม่พอ ค่อยเทียบ MILP ด้วยข้อจำกัดเดียวกัน รายงานกรณีไม่มีคำตอบและ timeout ด้วย ห้ามตัดกรณีล้มเหลวออกเพื่อเพิ่มอัตราผ่าน
- ยังไม่มีผลทดสอบรุ่นใหม่หรือผลความพึงพอใจ จึงยังสรุปไม่ได้ว่าแก้สมบูรณ์หรือพร้อมใช้งานทุกกลุ่ม

## ผลกระทบต่อเล่ม

ตรวจเอกสาร architecture/related-work ใน repository แล้ว แต่ยังไม่พบไฟล์เล่มฉบับส่ง จึงระบุเลขหน้า/ย่อหน้าจริงที่ต้องแก้ไม่ได้

- เมื่อเปลี่ยน template, portion policy หรือ objective ต้องแก้คำอธิบายวิธีจัดเมนูและเหตุผลอ้างอิงให้ตรงรุ่นจริง แม้ยังใช้ coordinate descent เดิม
- เพิ่มการทดลองก่อน/หลังและข้อจำกัดของชุดประเมินในส่วนผล/อภิปราย เก็บผลเก่าในชื่อ baseline ไม่เขียนทับแล้วถือว่าเป็นผลรุ่นใหม่
- ไม่จำเป็นต้องเปลี่ยนวัตถุประสงค์หรือทำผล RAG ทั้งหมดใหม่โดยอัตโนมัติ ต้องตรวจว่าข้อสรุป/การทดลองใดเรียกตัวจัดเมนูหรือรับผลจากกฎที่เปลี่ยน แล้วทดสอบส่วนนั้นใหม่
- ถ้าเปลี่ยนเป็น MILP ต้องอธิบายตัวแปร constraint objective และการจัดการ infeasible/timeout เพิ่มอย่างชัดเจน จึงกระทบวิธีวิจัยมากกว่าการปรับกฎในวิธีเดิม

ลำดับเริ่มงานที่แนะนำ: ตรึง baseline → ทบทวน portion policy → แก้ template 3/4 มื้อ → เพิ่มคะแนนรายมื้อและ validator → เปรียบเทียบผล → พิจารณา solver ใหม่ตามหลักฐาน
