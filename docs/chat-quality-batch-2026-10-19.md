# ชุดปิดงาน Q2–Q4 และเตรียมทดสอบเว็บจริงรอบเดียว

ต่อจาก Q1 ใน `1b6b635` ชุดนี้แก้งานค้างที่ทำได้ในโค้ดรวมกัน แล้วตรวจ local/CI ก่อน deploy ครั้งเดียว การรับงาน production ยังต้องตรวจหลัง backend/frontend ขึ้นรุ่นเดียวกัน ไม่ใช้สถานะ Active หรือ health 200 แทนผลใช้งานจริง

เพิ่มข้อมูลสถานะอาหารเฉพาะผลลัพธ์เมนู ไม่เปลี่ยนค่าทางโภชนาการ น้ำหนักต่อหน่วย อาหารต้นทาง หรือสูตรเป้าหมาย ไม่สร้างระบบสูตรอาหารใหม่ และไม่แปลงน้ำหนักดิบ/สุกโดยไม่มีข้อมูล ชื่อ “วัตถุดิบ” ไม่ถูกนับเป็นหลักฐานว่าเป็นอาหารดิบ นโยบายการเลือกอาหารเปลี่ยนเป็น `practicality-v3`; prompt เป็น `v1.18.0`

## อ้างอิงสูตร Katch-McArdle

[Tang และคณะ (2025), ส่วน Data collection](https://www.frontiersin.org/journals/nutrition/articles/10.3389/fnut.2025.1543263/full) ระบุสมการ 370 + 21.6 × มวลไร้ไขมัน ตรงกับรูปสมการที่ระบบใช้ จึงเพิ่มลิงก์สำหรับตรวจรูปสมการในกรณีกรอกเปอร์เซ็นต์ไขมัน พร้อมระบุว่าเป็นงานที่ใช้สมการ ไม่ใช่ต้นกำเนิดสมการหรือการรับรองความแม่นยำสำหรับผู้ใช้ งานนี้เป็นการศึกษาผู้มีน้ำหนักเกิน/โรคอ้วน และไม่ได้วัด RMR ด้วย indirect calorimetry ไม่ยก Mifflin มาอ้างแทนสูตรนี้ ไม่ยืมตัวคูณกิจกรรม/พลังงานขาดดุลของงานนี้มาใช้ในแอป

## ผลตรวจรวมก่อนส่ง

- ชุด backend ทั้งหมดก่อนเพิ่ม FAQ สุดท้าย: **1580 ผ่าน**, 76 deselected ตามขอบเขต CI เดิม; หลังเพิ่ม FAQ ชุดที่กระทบคำตอบ/อ้างอิง **244 ผ่าน**, 1 deselected เพราะเป็น evidence audit ที่ต้องมีเอกสาร local ผล CI ของ commit สุดท้ายเป็นหลักฐานเพิ่มเติมแยกกัน
- Frontend **109 tests ผ่าน**; lint, TypeScript และ build ผ่าน
- Chrome กับ API/SQLite/SMTP ทิ้งได้จริง: **63 checks ผ่าน** สำหรับชุดคุณภาพ และ **41 checks ผ่าน** สำหรับสูตร/ลิงก์ รวม layout การเปิดประวัติ ข้อมูลโปรไฟล์ไม่เปลี่ยน และ cleanup บัญชีทดสอบ
- Candidate กับฐานอาหาร/ความรู้ production ใน transaction read-only: **18 สถานการณ์** ได้เมนู 6 แผน **24 มื้อ** ตรวจคูณกรัมกับค่าต้นทางซ้ำ ยอดตรงภายในปัดเศษ ทุกมื้ออยู่ในเพดานตัวอย่างเดิม ไม่อ่านหรือแก้ข้อมูลผู้ใช้ production
- อ่านคำตอบจริง 4 คำถาม: การโหลดกับไม่โหลด โปรตีนรวมต่อวัน กติกาไขมัน และ FAQ ครีเอทีน รอบแรกพบรายละเอียดเกินคำถาม/ถ้อยคำที่สื่อความเท่าเทียม จึงแก้และเก็บผลเดิมไว้ รอบสุดท้ายใช้ผล FAQ จาก `faq-integration.json` ส่วนอีก 3 คำถามใช้ `integration.json` รายละเอียดใน `quality-review.json` ไม่ใช้จำนวน assertions อ้างว่าคำตอบ AI ถูกต้องเสมอ
- ตรวจ DNS สาธารณะพบ DKIM, CNAME ส่งเมล, SPF และ DMARC policy `quarantine` อยู่ ไม่พบหลักฐานให้เดาเปลี่ยน DNS หรือลด DMARC; ยังไม่ได้อ่าน Authentication-Results ของเมลจริง จึงไม่สรุปว่า Spam หายสำหรับทุกกล่อง ตาม [Resend Deliverability Insights](https://resend.com/blog/deliverability-insights) ควรใช้ headers/Insights ของฉบับที่มีปัญหาประกอบ

หลักฐาน local: `output/chat-quality-batch-20261019/`, `output/playwright/chat-quality-batch-20261019/`, `output/ci-cd/chat-quality-batch/test-results/` เพิ่ม `npm run test:quality-ui` เป็น gate ใน frontend CI ชุดอ้างอิงเดิมอัปเดตให้ตรวจลิงก์ Katch ตามหลักฐานใหม่ ไม่ลดการตรวจว่าใช้สูตรผิดแหล่งไม่ได้

## ขอบเขตที่ยังไม่ใช่บั๊กที่ปิดด้วยแพตช์

- ยังไม่มีฐานราคา จึงรับรองงบไม่ได้ ต้องมีราคา/ปริมาณ/พื้นที่และวันที่จริงก่อนพัฒนาการจัดตามงบ
- วีแกนร่วมกับแพ้ถั่วเหลืองยังอาจไม่มีโปรตีนที่รองรับ ต้องคงการปฏิเสธ ไม่ปลดข้อแพ้เพื่อสร้างเมนู
- ชื่อ/ประเภทอาหารไม่ใช่ข้อมูลส่วนผสมและการปนเปื้อนทุกยี่ห้อ ต้องตรวจฉลากและใช้งานตามข้อจำกัดที่แจ้ง
- Inbox placement ขึ้นกับผู้รับและระบบอีเมลด้วย การมี DNS ครบ/ส่ง Delivered ไม่เท่ากับรับรอง Inbox
- ไม่รับรองความเหมาะสมทางคลินิกทุกแผนหรือว่าคำตอบ AI ไม่มีข้อผิดพลาดทุกครั้ง ยังต้องมีผู้เชี่ยวชาญตรวจรับก่อนอ้างเชิงคลินิก

ไม่มี migration หรือ Variables ใหม่ รุ่นนี้รวม Q1 และแพตช์แยกชนิดถั่วก่อนหน้าไว้แล้ว แผนรับงานเว็บจริงรอบเดียว: สมัคร OTP → ตั้งโปรไฟล์ → ตรวจคำตอบสูตร/ที่มา → BMI ต่ำ → เพิ่มกล้าม/มื้อเสริม → วีแกน/ข้อแพ้ → งบ → FAQ/หลักฐาน → ประวัติและไดอารี่ → logout/recovery/cleanup โดยใช้บัญชีทดสอบเดียวที่เจ้าของควบคุม ไม่แตะบัญชีจริงเดิม
