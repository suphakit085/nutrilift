# แก้การอ่านข้อจำกัดอาหารจากข้อความไทย — 18 ตุลาคม 2569

แก้ H1 จาก UAT แชต: คำขอปกติ เช่น “ไม่ใช้อาหารเสริม ขอปริมาณอาหารและยอดพลังงานโปรตีนรวม” ถูกอ่านเป็นการงดอาหารชื่อ “ยอดพลังงานโปรตีนรวม” ทำให้ปฏิเสธเมนู และอ่านข้อจำกัดปลอมซ้ำเมื่อถามต่อในห้องเดิม

## วิธีแก้

ปรับ parser แบบ deterministic ใน `backend/app/services/menu_context.py` ไม่เพิ่มข้อยกเว้นเฉพาะประโยคจาก UAT และไม่ส่งการตัดสินข้อแพ้ให้โมเดลเดา

- ใช้คำบอกการขอผลลัพธ์พร้อมหัวข้อ เช่น “ขอปริมาณ”, “พร้อมยอดรวม”, “แสดงชื่ออาหาร” เป็นขอบเขตจบข้อห้ามอาหาร ก่อนนำรายการไปแยกด้วยคำเชื่อม
- หลีกเลี่ยงการตัดด้วยคำขึ้นต้นสั้น ๆ อย่าง “ขอ” หรือ “บอก” เพียงอย่างเดียว เพราะอาจเป็นส่วนของชื่ออาหารที่ระบบยังไม่รู้จัก เช่น “ของหมัก”, “บอกฉ่อย”
- คำกำกวม “งด” ตรวจขอบเขตคำด้วยตัวตัดคำไทย `newmm` จาก PyThaiNLP ที่มีใน dependencies อยู่แล้ว ใช้พจนานุกรมในเครื่อง ไม่ต้องเพิ่มบริการ AI หรือดาวน์โหลดข้อมูลระหว่าง parse ป้องกันการจับคำสั่งงดจากบางส่วนของ “อ้างอิงด้วย”, “แตงดอง”, “งดงาม” และยังอ่านประโยคที่ไม่มีเว้นวรรคได้
- รองรับรายการข้อห้ามที่เชื่อมด้วย “หรือ”, “รวมถึง” และการย้ำว่า “และยังแพ้...” รวมถึง “ห้ามใช้” ในข้อความ UAT
- ข้อแพ้ที่ไม่รู้จักยังถูกบล็อก และยังคงอยู่เมื่อกลับไปใช้โปรไฟล์ที่บันทึก ไม่ละทิ้ง unknown เพื่อให้การจัดเมนูผ่าน
- อ่านประวัติผู้ใช้ด้วย parser ที่แก้แล้ว จึงแก้ห้องเก่าที่มีข้อความต้นเหตุได้ด้วย โดยไม่ย้ายหรือเขียนข้อมูลผู้ใช้ใหม่ ข้อความ error ที่เคยบันทึกไว้ยังเป็นประวัติเดิม

ส่วนที่แก้คือการตีความข้อจำกัดและขอบเขตคำขอ ไม่เปลี่ยนสูตรพลังงาน สารอาหาร ฐานอาหาร authentication หรือ schema ฐานข้อมูล ไม่มี migration

## หลักฐานทดสอบก่อนและหลังแก้

เพิ่ม `backend/tests/test_menu_constraint_boundaries.py` จำนวน 90 กรณี ตรวจทั้งคำขอที่เคยพังและการไม่ทำให้ข้อแพ้หาย รวมถึงการเว้นวรรค/ขึ้นบรรทัดในคำแจ้งแพ้ภาษาอังกฤษ ก่อนแก้ กรณีจาก UAT ทั้ง 5 ข้อไม่ผ่านการตรวจ restrictions; หลังแก้ผ่านและเรียก planner จริงได้

| สิ่งที่ตรวจ | ผล |
|---|---|
| กรณีใหม่ + ชุดเดิมด้านบริบท/มื้อ/ข้อห้าม | 179 ผ่าน |
| backend regression ตามคำสั่ง CI (`not postgres and not evidence`, ยกเว้น source PDF audit) | 1,363 ผ่าน, 70 deselected |
| Ruff สำหรับ backend app/tests/ingest | ผ่าน |
| โมเดล Gemini จริง + RAG จริง + อาหารในฐานข้อมูลจริง โดยรัน candidate service | 5/5 ผ่าน: UAT 02, 03, 08, 11, 12 |
| คำนวณสารอาหารย้อนกลับจากปริมาณและค่าต้นทางของคำตอบโมเดลจริง | 16 มื้อจาก 5 กรณี ตรงในระดับการปัดเศษที่แสดง |
| การใช้คำขอต้นเหตุในประวัติห้องเดิม | ผ่าน รวมคำถามไม่กินไก่และเพิ่มแพ้นมวัว |
| unknown allergy, ข้อแพ้หลายอย่าง, reset, assistant สั่งเอง, ห้องใหม่ | ผ่าน |

การทดสอบโมเดลจริงใช้โปรไฟล์จำลองและ connection ที่ตั้ง `SET TRANSACTION READ ONLY` ทุก transaction ไม่มีการสร้างบัญชี ส่งอีเมล หรือเขียนข้อมูลบน production ผลนี้เป็น service integration ของโค้ด candidate **ยังไม่ใช่หลักฐานว่า backend บน Railway ใช้แพตช์นี้แล้ว**

หลักฐาน local: `output/menu-constraints-20261018/live-readonly.json` และ `output/ci-cd/menu-constraints/test-results/*.xml` ไฟล์เหล่านี้ไม่รวมในแพตช์สำหรับ deploy

## ขอบเขตที่ยังต้องติดตาม

Parser ยังเป็นกฎและตัวตัดคำ มีรายการคำบอกเจตนา จึงไม่รับประกันว่าจะเข้าใจภาษาไทยอิสระทุกประโยค การเพิ่มกรณีทดสอบช่วยป้องกันปัญหาที่พบกลับมาและตรวจการละข้อแพ้ ส่วน H2 ที่ AI บางครั้งสร้างเมนูโดยไม่เรียก planner เป็นงานถัดไปและไม่ได้อ้างว่าแก้ในแพตช์นี้

หลัง deploy ต้องส่งข้อความ UAT เดิมผ่านบัญชีทดสอบบนเว็บจริง ตรวจ tool outcome, จำนวนมื้อ, ข้อแพ้และคำถามต่ออีกครั้ง ก่อนปิดผล H1 บน production
