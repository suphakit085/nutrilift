## นโยบายปริมาณและที่มา

ตัวเลขต่อไปนี้เป็น **ขอบเขตของผลิตภัณฑ์ที่ผู้พัฒนากำหนดและยังรอนักกำหนดอาหารทบทวน** ไม่ใช่ตัวเลขที่อนุมานว่ารับรองโดยบทความวิจัย งานวิจัยในรายงานข้อเสนอสนับสนุนการพิจารณาปริมาณและโครงสร้างมื้อ ไม่ได้เป็นแหล่งยืนยันช่วงกรัมเหล่านี้

| ชนิดที่นโยบายครอบคลุม | ช่วงอนุญาต (กรัม) | ช่วงที่ให้คะแนนชอบ (กรัม) | ขั้นกรัม |
| --- | --- | --- | --- |
| โปรตีนหลักทั่วไป | 50–300 | 75–200 | 25 |
| โปรตีนพืช/ถั่วในบทบาทโปรตีน | 75–300 | 100–250 | 25 |
| ผงอาหารเสริมโปรตีน | 20–70 | 20–40 | 25 หรือจำนวนเต็มเมื่อมีหน่วยสกู๊ป |
| แป้งทั่วไป | 75–400 | 100–300 | 25 |
| ขนมปัง | 50–200 | 50–150 | 25 |
| ผลไม้ | 50–300 | 75–200 | 25 |
| ผัก | 50–250 | 75–200 | 25 |
| ถั่ว/เมล็ดในบทบาทไขมัน | 10–60 | 15–35 | 5 |
| ไขมันเติม เช่น น้ำมัน/เนย | 2.5–20 | 5–15 | 2.5 |
| กรณีที่ใช้ fallback ของบทบาท | ขั้นต่ำเดิมตาม slot ถึงไม่เกิน 110 | 20–80 | 25 |

ขอบเขตจริงตัดร่วมกับ cap ของมื้อ และขอบเขตหน่วยนับที่มีอยู่ เช่น อาหารนับฟอง/สกู๊ปต้องเป็นจำนวนเต็ม ภาพรวมนี้ยังเป็นกฎตามชนิด/บทบาทอาหาร ไม่ใช่ฐาน portion policy ราย food ID ที่ผู้เชี่ยวชาญรับรองครบทุกแถว น้ำหนักหมายถึงสภาพอาหารตามข้อมูลต้นทาง ไม่มีการแปลงน้ำหนักดิบเป็นสุกเอง

คะแนนการกระจายใช้สัดส่วนตัวอย่าง 3 มื้อ 30/35/35% และ 4 มื้อ 25/30/30/15% สำหรับพลังงานและโปรตีน ยอมให้เบี่ยงได้ 25% ของสัดส่วนมื้อนั้นก่อนเริ่มคิดคะแนน เป็น soft preference ที่ปรับได้ ไม่บังคับทุกมื้อเท่ากันหรือกำหนดเพดานโปรตีนทางคลินิก

## ผลทดสอบและขอบเขตของหลักฐาน

ชุดเปรียบเทียบหลักตรึง targets ก่อนทดลอง: 2 เพศ × 3 เป้าหมาย × 9 ชุดข้อจำกัด × 3 variants × 2 จำนวนมื้อ = **324 กรณี** ใช้ข้อมูลอาหารเดียวกัน 386 แถว และตรวจว่าไฟล์ต้นทางไม่เปลี่ยนระหว่างรัน

| ตัวชี้วัดในชุดหลัก | Baseline | รุ่นปรับปรุง |
| --- | ---: | ---: |
| เข้าเกณฑ์สารอาหารรายวัน โหมด 3 มื้อ | 162/162 | 162/162 |
| เข้าเกณฑ์สารอาหารรายวัน โหมด 4 มื้อ | 162/162 | 162/162 |
| จำนวนรายการโปรตีนหลักในมื้อหลักต่ำกว่า 50 กรัม | 730 | 0 |
| จำนวนรายการแป้งเกิน 400 กรัม | 130 | 0 |
| รายการที่ละเมิดตัวกรองข้อจำกัดอาหารในฐานข้อมูล | 0 | 0 |
| แผนที่อยู่ในช่วงความชอบการกระจายครบทั้งพลังงานและโปรตีน 3 มื้อ | 7/162 | 76/162 |
| แผนที่อยู่ในช่วงความชอบการกระจายครบทั้งพลังงานและโปรตีน 4 มื้อ | 0/162 | 16/162 |

จำนวนรายการนับรวมแผนทุก variant และจำนวนมื้อ ไม่ใช่จำนวนผู้ใช้จริง ชุดหลักใช้ขนาดร่างกายเพียงสองแบบ ไม่ใช่ตัวแทนของทุกโปรไฟล์ เกณฑ์การกระจายเป็นนิยามของระบบและคำนวณจากค่าที่แสดงพร้อมเผื่อการปัด ไม่ใช่การยืนยันประโยชน์ต่อสุขภาพ แผนที่ไม่ผ่าน soft preference ยังแจ้งข้อจำกัดในแชต ไม่ถูกเรียกว่าสมดุลสมบูรณ์

Mean squared distance ของสัดส่วนพลังงาน/โปรตีนจากสัดส่วนตัวอย่างลดจาก 0.1160 เป็น 0.0174 สำหรับ 3 มื้อ และจาก 0.1118 เป็น 0.0215 สำหรับ 4 มื้อ เป็นเพียงตัวชี้วัดเชิงคำนวณตาม objective ที่เพิ่ม ไม่ใช่คะแนนความพึงพอใจ

ชุดโปรไฟล์เพิ่มเติม 10 กรณีซึ่งไม่ได้ใช้ปรับนโยบายก่อนรัน: จัดแผนเข้าเกณฑ์ได้ 7 กรณี แผนชาย 110 กก./195 ซม. กิจกรรม active เป้าหมาย bulk จำนวน 3 มื้อยังเข้าเป้าไม่ได้ และรายงาน `within_tolerance=false` ตามจริง ส่วน 4 มื้อผ่าน อีก 2 กรณีวีแกนร่วมแพ้ถั่วไม่มีแหล่งโปรตีนที่ผ่านตัวกรอง จึงคืนข้อผิดพลาดที่จัดการได้ ไม่ฝืนแนะนำอาหารต้องห้าม

Local timing ของชุดหลัก: median 0.239 วินาที, p95 ประมาณ 0.500 วินาที, สูงสุด 3.115 วินาที ขณะมีงานทดสอบอื่นร่วมรัน ตัวเลขนี้ไม่ใช่ load test หรือ SLA ของ production

Backend regression ผ่าน **1,101 ข้อ** (เว้นกลุ่ม PostgreSQL/evidence และโมดูล audit ที่ต้องใช้เอกสารต้นฉบับในเครื่อง ตามขอบเขต CI เดิม) ชุดตรวจร่วมกับงาน auth/ประวัติโปรไฟล์ที่อยู่ใน workspace ผ่าน **188 ข้อ** โดยไม่รันกลุ่ม PostgreSQL ผลสองชุดมีข้อทดสอบซ้ำกัน จึงไม่นำจำนวนมาบวกเป็นยอดข้อทดสอบอิสระ

ผลทดสอบบันทึกใน XML ภายใต้ `output/meal-plan-practicality-20261017/` การทดสอบแชต 4 กรณีเรียก planner และเครื่องคำนวณจริง โดย stub เฉพาะผู้ให้บริการโมเดลและการอ่านแถวอาหาร ไม่ใช่การทดสอบ Gemini หรือ API production จริง Ruff และ `git diff --check` ผ่าน มี deprecation warning ของ TestClient และใน workspace มี warning เรื่องสิทธิ์เขียน pytest cache แต่ไม่มี test failure

## การทำซ้ำและไฟล์หลักฐาน

สคริปต์ที่เพิ่ม: `eval/meal_plan_practicality.py`

```powershell
backend/.venv/Scripts/python.exe eval/meal_plan_practicality.py --backend-dir backend --foods knowledge/foods.csv --cases output/meal-plan-practicality-20261017/cases.json --output output/meal-plan-practicality-20261017/after.json
```

ครั้งแรกใช้ `--write-cases` เพื่อสร้าง targets ตามวันที่รัน จากนั้นใช้ไฟล์ cases เดิมทั้งก่อนและหลัง ห้ามสร้าง targets ใหม่ระหว่างเปรียบเทียบคนละรุ่น Baseline ตรึงสำเนาโมดูลไว้ใน `output/meal-plan-practicality-20261017/baseline-backend/` และตรวจว่า hash ของตัวจัดเมนูตรงกับไฟล์ที่ใช้รัน baseline ครั้งแรก

- `cases.json`: อินพุตชุดหลักและ targets ที่ตรึงไว้
- `before.json`: baseline รอบแรกก่อนพัฒนา
- `before-reproduced.json`: ทำซ้ำ baseline ด้วยสคริปต์รายงานฉบับเดียวกับรุ่นใหม่
- `after.json`: ผลรุ่นสุดท้ายครบ 324 กรณี พร้อม hash และ outputs เต็ม
- `additional-cases.json`, `additional.json`: โปรไฟล์เพิ่มเติมและกรณีไม่มีคำตอบ
- `comparison.json`: สรุปก่อน/หลังและ timing
- `backend.xml`: ผล backend regression
- `workspace-compatibility.xml`: ผลตรวจร่วมกับงาน auth/ประวัติโปรไฟล์ใน workspace
- `workspace-before.json`: hash ของไฟล์ที่มีงานค้างอยู่ก่อนนำการแก้นี้เข้า workspace เพื่อช่วยตรวจว่าไม่เขียนทับงานอื่น
- `workspace-preservation.json`: ยืนยันไฟล์งานค้างอื่นไม่ถูกเปลี่ยนและฟังก์ชันแชตที่เกี่ยวข้องตรงกับรุ่นที่ทดสอบ

ผลระหว่างพัฒนา (`iteration-*.json`) เป็นหลักฐานทดลองระหว่างแก้ ไม่ใช้แทนผลรุ่นสุดท้าย รุ่นที่เพิ่มข้อจำกัดอย่างเดียวทำให้บางแผนไม่เข้าเป้า จึงเพิ่มการปรับสองรายการ อนุญาตละโปรตีนเสริมมื้อว่าง และลองอาหารทดแทนแบบจำกัด ก่อนยืนยันผลชุดสุดท้าย

## การเชื่อมกับส่วนอื่นและงานที่เหลือ

- เป้าสารอาหารยังมาจาก `nutrition.py` ตามโปรไฟล์เดิม ตัวกรองข้อจำกัดยังทำก่อนเลือกอาหาร ตารางแชตใช้ `_menu_reply` เดิมและเพิ่มข้อความข้อจำกัดที่เกี่ยวข้อง
- ไม่มี migration หรือ dependency ใหม่ ไม่ได้แก้ข้อมูลอาหารต้นฉบับ ค่าเป้าหมายโปรไฟล์ ระบบ auth หรือประวัติบันทึกอาหาร
- CI backend เพิ่มการ lint ไฟล์ที่เปลี่ยนและทดสอบใหม่ผ่าน regression suite เดิม รวม trigger เมื่อสคริปต์ประเมินหรือข้อมูลอาหารเปลี่ยน การยืนยันในรายงานนี้เป็นผล local ยังไม่ใช่ GitHub Actions run ของรุ่นนี้
- ยังต้องมีผู้เชี่ยวชาญทบทวนช่วงปริมาณรายอาหาร และผู้ใช้เป้าหมายประเมินความเหมาะสมของรายการอาหารพร้อมปริมาณ
- ยังไม่ใช้ MILP และไม่อ้างว่า heuristic หาแผนได้ทุกโปรไฟล์ การไม่มีคำตอบไม่ใช่เหตุให้ผ่อนข้อห้ามการแพ้
- เอกสาร `architecture.md` ปรับวิธีให้ตรงโค้ดแล้ว ส่วนเล่มฉบับส่งยังไม่พบใน workspace จึงยังไม่ได้แก้ไฟล์เล่มจริง ควรปรับวิธีและผลทดลองที่ได้รับผลกระทบ โดยคงผลเดิมเป็น baseline

แนวคิดและเอกสารต้นทางอยู่ใน [รายงานข้อเสนอ](meal-plan-practicality-recommendation-2026-10-17.md) ตัวเลขกรัมในรุ่นนี้ยังเป็นนโยบายของผลิตภัณฑ์ ไม่ใช่การยืมข้อรับรองทางคลินิกจากบทความเหล่านั้น

## ขอบเขตที่ผู้ใช้ยืนยันหลังการหารือ

ผู้ใช้ต้องการคงเมนูแบบเดิม: ตารางรายการอาหารพร้อมปริมาณและสารอาหารจากฐานข้อมูลที่มีอยู่ จึงไม่เพิ่มฐานสูตรอาหาร ขั้นตอนปรุง หรือระบบจัดเมนูจากสูตร ข้อเสนอเรื่องสูตรอาหารในรายงานวิจัยเป็นทางเลือกนอกขอบเขตงานปัจจุบัน ไม่ใช่ข้อกำหนดก่อนใช้งานรูปแบบเดิม

งานที่เกี่ยวข้องต่อไปจำกัดอยู่ที่การทบทวนขนาดส่วน การกระจายรายมื้อ การลองรายการอาหารทดแทน และการแจ้งเมื่อแผนยังเข้าเป้าไม่ครบ การคงรูปแบบเดิมไม่ใช่การย้อนแพตช์แก้การคำนวณ 3/4 มื้อหรือการตรวจตัวเลขที่ทำแล้ว

การยืนยันขอบเขตครั้งนี้แก้เอกสารเท่านั้น ไม่มีการแก้โค้ด runtime หรือ deploy เพิ่มเติม ผลทดสอบของ implementation commit `c6c9a73` จึงยังเป็นหลักฐานของโค้ดรุ่นเดิมที่บันทึกไว้
